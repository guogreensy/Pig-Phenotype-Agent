# 技术报告：检索增强生成与工具调用在猪只表型分析中的实现

> 本报告描述系统**如何实现**，以及每个关键选择的依据。所有数字均可从仓库产物复核：
> 知识库产物在 `data/kb/`，实验记录在 `results/agent/runs/`，指标在 `results/metrics/`，
> 图表在 `results/figures/`。实验的**结果分析**见[《实验报告》](experiment_report_agent.md)。

---

## 0. 摘要

本系统在已完成的视觉姿态识别系统之上，构建了一层"检索增强 + 工具调用"的智能助手，使大模型能够查询养殖数据、检索本地文献、调用视觉模型识别图片，并把每个结论落到可核查的来源上。

技术要点：

1. **知识库**：20 篇可追溯来源的文献与项目文档，切成 943 个片段；稠密（2048 维向量，精确余弦）+ 词法（字符 n-gram TF-IDF）双索引，加权 RRF 融合，异常时自动降级。
2. **工具层**：8 个工具，统一契约，参数白名单校验，异常不外抛，未注册工具名被拒绝并回传可用清单。
3. **Agent**：单循环"模型→工具→模型"，步数与调用双重预算，重复调用拦截，步数耗尽后强制收尾且不允许编造。
4. **可观测**：每次对话落盘完整轨迹（工具参数、耗时、token、提示词指纹），支撑 90 次对照实验与 478 项单元测试。

规模：源码 27 个文件 6,719 行，脚本 15 个 3,833 行，测试 27 个文件 5,205 行。

## 1. 问题定义

第一阶段的结论是：视觉大模型识别姿态的准确率只有 37.7%（四分类随机水平 25%），且"坐姿"这一类的 F1 为 0。也就是说，单靠视觉模型无法支撑养殖场的实际决策。

要让大模型在这类场景里可用，必须解决三类问题：

| 问题 | 本质 | 本项目的解法 |
|---|---|---|
| 模型不知道具体数据 | 参数里没有"P2-007 昨天吃了多少" | 工具调用（可执行的数据查询） |
| 模型不知道本地知识 | 参数里没有这 20 篇文献 | RAG（检索增强） |
| 模型会编造 | 无证据时给不出"不知道" | 来源标注 + 拒答判定 + 提示词约束 |

这三件事的工程难度不在"调用一次模型"，而在**让模型稳定地在正确的时机调用正确的工具，并把结果如实转述**。本报告即围绕这一点展开。

## 2. 总体架构

### 2.1 分层

```
Web 界面（tornado 单页，4 区块）
      │ /api/predict、/api/agent
Agent 层（planner / executor / report）
      │ function calling（JSON Schema）
工具层（registry + 8 个工具）
      │
知识层（corpus → dense / lexical → retrieve）
```

### 2.2 为什么是单循环而非多智能体

任务边界是清晰的：查数、查文献、看图。单循环（模型自主决定调哪个工具、调几次）足以覆盖，且：

- 多智能体需要额外的角色提示词与消息中转，在免费模型上延迟翻倍；
- 单循环的轨迹更短，便于逐条记录与复核；
- 本项目要证明的是"工具+检索有效"，不是"编排框架先进"。

### 2.3 一次问答的执行路径

```
build_messages(question)
  → system 提示词 = 模板 + 8 个工具的 JSON Schema + 7 条硬规则 + 数据时间范围
  → chat(messages, tools)
      ├─ 返回 tool_calls：逐条校验参数 → 执行 → 结果作为 tool 消息回填 → 继续 chat
      └─ 返回文本：结束，得到回答
  → build_report：抽引用、判来源、汇总指标
```

## 3. 知识库构建

### 3.1 语料获取

抓取阶段（`scripts/fetch_corpus.py`）逐个来源实测：

| 来源 | 结果 |
|---|---|
| PMC E-utilities | ✅ 唯一可稳定获取论文的渠道，13 篇 |
| arXiv | ❌ 持续 429 / 超时 |
| BioRxiv | ❌ 返回空结果 |
| Frontiers | ⚠️ 需逐篇构造 URL，未采用 |
| 维基百科 / 百度 / 知乎 | ❌ 不可达 |

最终语料 20 篇：13 篇 PMC 论文 + 6 篇本项目自有文档 + 1 篇 HF 数据集说明。

物种过滤：抓取到的 2 篇非猪论文（牛、家禽）被剔除，避免污染检索结果。

许可处理：PMC 的 JATS 许可码（`ccbylicense` 等）在抽取时统一映射为可读形式（CC BY / CC BY-NC / CC BY-NC-ND），并在引用中展示。这一步是后补的——最初引用里直接显示 `ccbylicense`，用户看不出许可含义，因此补了 `normalize_license` 并重建了受影响的索引。

| 项 | 数值 |
|---|---:|
| 文档数 | 20 |
| 正文字符 | 569,057 |
| 片段字符合计 | 568,555 |
| 片段数 | 943 |
| 片段长度（最小/中位/最大） | 67 / ~719 / 867 |

"正文字符"与"片段字符合计"是两个口径：前者在清洗后由构建脚本统计，后者可由 `chunks.jsonl` 直接求和复核。两者相差 502 字符，不应混用。

### 3.2 分块策略

分块质量直接决定检索质量，这里踩过三个坑，都改掉了：

| 问题 | 现象 | 修法 |
|---|---|---|
| 句中硬切 | 片段以半个单词/半句话结尾 | 以段落为累积单位，接近上限时收口 |
| 单句绕过上限 | 一个超长句直接成为一个超长片段 | 超长段按句子边界二次切分 |
| 切点等于末尾 | 最后一个片段被丢弃 | 修正 `cut == end` 时的 flush 逻辑 |

参数：目标 800 字符，保留章节标题与字符区间。

### 3.3 双索引

**稠密索引**（`src/rag/dense.py`）

- 嵌入模型：智谱 `embedding-3`，2048 维；
- 943 × 2048 float32 矩阵，`.npz` 存储，6.1 MB；
- 检索：全量点积 + 精确排序，单次约 1 ms；
- 为什么不用近似索引：943 条规模下精确检索更快、更准，且不引入新依赖（Chroma 未安装）。

建设成本：**144,651 个 embedding token**。因许可归一化需要重建语料，这笔成本实际付了两次（第一次 144,651，重建后 144,651），如实记录在 `logs/`。

**词法索引**（`src/rag/lexical.py`）

- `TfidfVectorizer(analyzer="char_wb", ngram_range=(2,3), sublinear_tf=True)`；
- 28,932 个特征，4.2 MB（pickle）；
- 为什么用字符 n-gram：未安装 jieba，字符级 2–3 gram 在中文短查询上召回稳定，且无需词典。

**指纹机制**

两个索引都记录 `chunks.jsonl` 的 SHA256。`build_kb.py --status` 据此判断是否需要重建：

- 优先内容指纹，mtime 仅作为旧产物的兜底；
- 原因：`python -m src.rag.corpus` 会重写 `chunks.jsonl`，内容不变但 mtime 变了，仅看 mtime 会误判为过期。

### 3.4 融合检索

加权 RRF：`score = w_dense/(K+r_dense) + w_lexical/(K+r_lexical)`，`K=60`，`w_dense=1.0`，`w_lexical=0.5`，词法额外设 `LEXICAL_MIN_SCORE=0.01`。

**为什么不等权**：初版用等权 RRF，结果是中文短查询（如"猪只姿态识别"）的词法 Top-1 常常是无关文档——字符 n-gram 撞上了"数据集/识别/本系统"这类高频字。等权把噪声顶到了语义结果前面。加权 + 下限后，稠密结果稳定占优，词法只负责补充召回。

### 3.5 降级设计

`mode="auto"` 时，稠密路径的任何异常（无密钥、接口失败、索引缺失）都转词法，并带 `fallback_reason` 与 `degraded=true` 向上传递。

**这是"不崩"而不是"等价"**：词法兜底在中文查询上的排序质量明显低于稠密路径。实验期共触发 21 次降级（rag 条件 16 次、full 条件 5 次），全部未中断对话，但相关性受损。这一点在实验报告里作为限制写明，而不是隐去。

### 3.6 一键构建

`scripts/build_kb.py` 编排四阶段：`fetch → chunks → lexical → dense`。

设计要点：

- 每阶段有"就绪"判定（文件存在 + 指纹一致 + 条数匹配）；
- **状态在循环内逐阶段重新检查**：最初只在循环前算一次状态，导致重建 `chunks` 后 `lexical`/`dense` 被误判为"已就绪"而跳过，留下不一致的知识库。已修，并补了回归测试。
- `--only` / `--skip` / `--force` / `--limit` / `--status` 支持增量与诊断。

## 4. 工具层

### 4.1 契约

```python
ToolSpec(name, description, parameters, handler, returns)   # 参数为 JSON Schema 子集
ToolResult(ok, tool, data, error, duration_ms, args)        # 统一返回信封
```

三条硬约束：

1. **参数白名单校验**：只接受 Schema 中声明的字段；类型、枚举、范围、必填、默认值逐项检查；`bool` 不当作 `integer`（Python 里 `True == 1`，容易放过错误参数）。
2. **异常不外抛**：处理器内部任何异常都被捕获并转为 `ok=false`，因为一次工具失败不应该让整个对话崩溃。
3. **未注册工具直接拒绝**，并把可用工具清单回传给模型，让它自我纠正。

第 3 条在实验里真的用上了：rag 条件有一次模型自创了 `analyze_image`（不存在的工具），注册表返回"未注册的工具，可用：search_knowledge、fetch_passage"，模型随后改用正确工具。

### 4.2 模拟数据集

真实猪场逐日数据无法获取且涉及隐私。本项目需要的是**可验证的数值口径**，因此构造了固定种子的模拟数据集：

| 项 | 值 |
|---|---|
| 种子 | 20261107 |
| 范围 | 2026-10-08 至 2026-11-06（30 天） |
| 规模 | 4 栏 × 12 头 = 48 头，1,440 条日记录 |
| 指标 | 体重、采食、饮水、活动指数、躺卧比例、温度、湿度 |
| 注入异常 | P3 栏第 18–24 天热应激（温度 +4.5℃、饮水 +25%、采食 −12%）；P2-007 自第 20 天采食 −35%；P4-003 自第 12 天活动 −0.22 |

注入异常的作用是**给实验提供确定的标准答案**：只有当"哪头猪异常"有唯一正确答案，指认类题目才可评分。

每条数据类工具返回都强制注入 `source="simulated"` 与免责声明，不依赖模型自觉标注。

### 4.3 8 个工具

| 工具 | 关键参数 | 说明 |
|---|---|---|
| `list_pens` | — | 栏位与猪只清单 |
| `query_pig_records` | 猪号/栏位/日期/指标/limit | 明细，默认 50 条 |
| `aggregate_metric` | 指标/分组/统计量/日期 | `mean/min/max/sum/count` |
| `detect_anomalies` | 指标/范围/天数/阈值 | z 分数，默认 2.0 |
| `analyze_pig_posture` | 图片路径/提示词方案 | 转述视觉模型判断 |
| `list_sample_images` | 类别/limit | 样本图清单 |
| `search_knowledge` | 查询/k/模式 | 返回摘要片段 |
| `fetch_passage` | chunk_id | 取回完整原文 |

**两级检索**：`search_knowledge` 只回约 400 字符摘要，需要原文时再调 `fetch_passage`。好处是 token 可控，且"是否深入某篇文献"成为模型的显式动作，便于观测。

**路径安全**：`analyze_pig_posture` 只接受 `data/` 目录内的路径。实现上**先判断包含关系、再判断是否存在**——顺序反了会通过报错泄露目录外文件是否存在。

### 4.4 视觉工具的边界

视觉工具不"改进"模型判断，只做三件事：路径校验、图片预处理（最长边 512、质量 90）、结果解析与 Schema 校验。

第一阶段的实测（200 样本、三组提示词）表明模型能力有限：最佳准确率 37.7%、Macro-F1 0.232，且严重偏向"侧卧"（recall 0.836 / precision 0.321）。因此本阶段把视觉工具定位为"参考"，并在界面上明确标注"模型判断，非人工标注"。

## 5. Agent 层

### 5.1 提示词

系统提示词 = 模板 + 工具 Schema + 硬规则 + 数据时间范围。

七条硬规则中，有四条是**在开发过程中被真实失败逼出来的**：

| 规则 | 触发它的失败 |
|---|---|
| 涉及数据/事实先调工具 | 无工具时模型编造不存在栏位的数据 |
| 统计量优先由工具算，不自己心算 | 模型把 7 条记录心算成 1.69，实际 1.626 |
| 方法/数字只能来自同一片段 | 模型把不同论文的方法合并到一条引用下 |
| 明确说明"数据为模拟" | 早期回答把模拟数据当作真实场户数据陈述 |

提示词随工具数量切换：无工具时不能要求"先调用工具"（自相矛盾），改为要求明确说明不确定。这个矛盾最初真的存在，是"直接回答"条件下模型反复声明"我需要工具"的直接原因。

提示词文本计算 `sha256` 并写入每条实验记录，保证"哪次对话用了哪版提示词"可查。

### 5.2 执行循环

```python
for step in range(max_steps):
    response = client.chat(messages, tools=schemas)
    if response.ok and response.tool_calls:
        for call in response.tool_calls:
            result = registry.call(call.name, call.arguments)   # 校验 + 执行 + 记日志
            messages.append(tool_message(call.id, result.to_message()))
        continue
    return answer(response.text)
```

预算：`max_steps=6`（实验用 5）、`max_tool_calls=8`、同一工具同一参数最多重复 2 次。

### 5.3 三处"不让自己骗自己"的设计

**（1）参数解析失败不静默**：模型返回的 `arguments` 若不是合法 JSON，记录 `parse_error` 并把原始串回填，让模型自己改正，而不是替它猜。

**（2）强制收尾不允许编造**：步数用尽后再发一次**不带工具**的请求，要求基于已有信息作答。如果这次它仍然请求工具，判定为失败（`model_error`），而不是接受一个空回答或让模型自由发挥。

**（3）工具失败如实回填**：工具返回 `ok=false` 时，错误原文进入消息历史，模型必须解释失败，不能拿推测替代。

### 5.4 报告层

`build_report` 做四件事：

1. **抽引用**：只采纳检索证据（`search_knowledge`/`fetch_passage` 的返回），按首次出现顺序编号、去重；
2. **判来源**：`uses_simulated_data` / `uses_vision` / `uses_knowledge` / `degraded` 由**程序判定**，不看模型怎么说；
3. **汇总指标**：模型调用数、工具调用数、token、耗时、停止原因；
4. **渲染**：Markdown 结构固定（问题/回答/引用/说明/运行信息）。

"由程序判定而非模型声明"是这一层的关键：模型可能声称"以上来自知识库"，但实际没调检索工具——这种情况在 `direct` 条件下必然发生，靠模型自述就会误判。

## 6. Web 集成

### 6.1 为什么不用 Gradio

`gradio 4.44` 要求 `pillow<11`，会把环境中现有 pillow 降级，影响同一环境下的其它项目。零安装约束下不引入，改用 tornado（随 Jupyter 已装）+ 原生 JS 单页。

### 6.2 助手接口 `/api/agent`

| 约束 | 实现 |
|---|---|
| 参数校验 | 问题非空 ≤500 字；`tools` 白名单；`max_steps` 夹取 1–8 |
| 不阻塞事件循环 | 放进 `run_in_executor`（tornado 单线程，直接跑会卡死界面） |
| 防止并发烧额度 | 进程级非阻塞锁，重复请求返回 429 |
| 缺密钥 | 直接返回阻塞原因，不进入任何"演示模式" |
| 未预期异常 | 返回 500 + 堆栈，不伪造回答 |

### 6.3 一个差点上线的严重缺陷

前端 JS 被 Python 字符串转义破坏：`INDEX_HTML` 是普通三引号字符串，JS 里的 `split('\n')` 被 Python 解释成真实换行，导致整个 `<script>` 块语法错误——**页面上所有交互都会失效**（包括原本正常的图片上传识别）。

HTTP 冒烟与单元测试都没能发现，因为它们只检查页面里有没有某些字符串、以及直接 POST 接口。最终用 `node --check` 对抽取出的 JS 做语法检查才暴露。

修法：`INDEX_HTML` 改为 raw 字符串（`r"""`），并加回归测试钉住（断言 JS 里必须是反斜杠 + n，而不是真实换行）。

### 6.4 界面

四区块：服务自检 / 图象识别 / 智能助手 / 提示词查看。

助手区支持选择工具组合（全部 / 仅数据 / 仅知识库 / 不用工具），与实验的三个条件一一对应，便于现场演示消融。

## 7. 工程决策汇总

| 决策 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| 前端 | tornado + 原生 JS | Gradio | pillow 版本冲突 |
| 向量检索 | numpy 精确余弦 | Chroma | 943 条规模无需近似；少一个重依赖 |
| 测试框架 | unittest | pytest | 标准库自带 |
| 中文分词 | sklearn 字符 n-gram | jieba | 已有依赖，无需词典 |
| 参数校验 | 自写白名单 | jsonschema | 只需 Schema 子集，约 90 行 |
| 检索主路径 | 稠密 | 词法 | 词法在中文短查询上噪声大 |
| Agent 形态 | 单循环 | 多智能体 | 任务边界清晰，避免额外开销 |
| PDF 解析 | 未使用 | PyMuPDF | 语料是 HTML/Markdown；装过但从未调用，收尾时已卸载 |

整个项目期间新增安装的第三方包只有 `pymupdf==1.24.14` 一个，**从未被调用，收尾时已卸载**。这一点如实记录，不假装"全程零安装"。

## 8. 质量保障

### 8.1 测试

478 项单元测试（5,205 行），覆盖：

| 层 | 测试内容 |
|---|---|
| 语料与分块 | 清洗、许可归一化、片段长度约束、字符统计口径 |
| 双索引 | 构建、保存加载、指纹一致性、空查询、维度校验 |

### 8.3 开发过程中发现并修复的缺陷

这些问题都不是"预想到的"，而是**验证时撞出来的**，列在此处是为了说明验证确实在起作用：

| 缺陷 | 如何发现 | 后果（若不修） |
|---|---|---|
| 前端 JS 被 Python 转义破坏 | `node --check` 语法检查 | 整页交互失效 |
| 分块句中硬切 / 单句绕过上限 | 分块产物人工抽查 | 检索质量下降 |
| 稠密索引静默加载默认 id 文件 | 加载路径测试 | 检索结果与语料错位 |
| 等权 RRF 噪声胜出 | 中文查询 Top-1 人工核对 | 检索结果不相关 |
| 知识库重建后下游未失效 | `--status` 一致性检查 | 索引与语料不一致 |
| `vision_tool` 导入不存在的常量 | 首次导入即报错 | 工具不可用 |
| `list_sample_images` 按目录名匹配失败 | 实际样本目录是 `split/label/` 两层 | 工具返回空 |
| 路径检查泄露目录外文件存在性 | 安全审查 | 信息泄露 |
| 许可显示为 JATS 代码 | 引用渲染时肉眼可见 | 用户看不懂许可 |
| 统计量被模型心算错（1.69 vs 1.626） | 与原始记录比对 | 报告数字错误 |
| 视觉题答案写在图片路径里 | 回答里模型自称"从路径可以看出" | 指标虚高 |

最后一条直接导致 15 次视觉题重跑，详见实验报告。

## 9. 已知限制

### 9.1 能力限制

| 限制 | 依据 |
|---|---|
| 视觉识别准确率低（37.7%） | 第一阶段 200 样本实测；坐姿 F1 = 0 |
| 检索语料仅 20 篇 | 抓取阶段只有 PMC 可稳定获取 |
| 词法兜底相关性差 | 中文查询常召回无关文档 |
| 模拟数据不可用于生产 | 数据为构造，非真实场户 |

### 9.2 工程限制

| 限制 | 说明 |
|---|---|
| 单进程并发 | 助手同时只处理一个提问，多人使用需队列 |
| 无对话上下文持久化 | 历史消息只在单次请求内使用 |
| 无流式输出 | 长回答需等完整生成（P95 达 168 秒） |
| 无重排序模型 | 融合后直接取 Top-k，未做 cross-encoder 重排 |
| 无多轮对话状态 | `history` 参数存在但界面未启用 |

### 9.3 后续可做

1. 加 cross-encoder 重排，提升 Top-5 精度；
2. 引入对话历史与指代消解，支持"那 P3 呢"这类追问；
3. 流式输出 + 工具调用进度推送，改善长延迟体验；
4. 扩充语料（若能稳定获取更多开放来源）；
5. 视觉模块换用更强的模型或做少样本提示，这一步需要新额度。

## 10. 结论

本项目的核心不是"接了几个工具"，而是把三件容易做假的事做成了可核查的：

1. **模型说"我不知道"时，是真的不知道**——拒答由工具返回与检索证据驱动，不是提示词祈祷；
2. **模型给的数字，能对回原始记录**——数据题期望值从原始数据独立计算，不进过工具；
3. **模型给的引用，能对回具体文献**——引用来自检索证据，编号可点击到原文。

代价也很清楚：调用次数增加 1.7–4.8 倍，P95 延迟从 40 秒升到 168 秒，且在缺少相应工具时模型会反复重试直到步数上限。这些代价与收益的量化对比见实验报告。
